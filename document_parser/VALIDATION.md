# 문서 파싱 개선·검증 기록

## 승인 범위와 업무 맥락

사용자는 현황 분석 후 HTTPX 클라이언트 교체, 명령·설정·저장 분리, 원본 페이지 번호와 manifest 보존, 기존 결과 보호, 테스트와 README 작성을 승인했다. 폴더명 변경은 구현 후 별도로 확인하기로 했다.

사용자는 이 코드가 행정안전부 주관 평가의 공공데이터 제공운영 영역 중 ‘AI 친화·고가치 데이터 개방 노력’ 지표에 대응하기 위해 작성되었다고 설명했다. 기관 문서를 기계학습에 유용하게 파싱하고 원문과 결과를 함께 개방하는 방안을 지원하는 목적이다. 기관명·실제 개방 건수·정량 성과는 확인되지 않았으므로 README에 추가하지 않았다. `reference/` 원본과 이력은 수정하지 않았다.

## 변경 내용과 영향

| 항목 | 구현 결과 | 영향 |
| --- | --- | --- |
| 실행 | `parse.py --input … --output …` | 작업 경로·출력 폴더를 명시하며, import와 도움말에는 API 키가 필요하지 않음 |
| 요청 | HTTPX AsyncClient와 요청당 제한 시간 | 기존 동기 API endpoint 사용. 연결·응답·전체 요청 제한을 적용하고 자동 재시도·리다이렉트 재전송은 하지 않음 |
| 기존 설정 | `document-parse`, `force`, Markdown, 차트 인식·좌표 활성, base64 목록 비움 | 기존 `langchain-upstage 0.7.7`의 요청 값과 대조. 모델 자체를 바꾸지 않음 |
| 문서별 차이 | PDF는 한 페이지씩 순차 요청, HWP/HWPX 등은 전체 요청 | 기존 `aload()` 경로의 PDF 단일 페이지 처리와 비PDF 전체 처리를 유지 |
| 페이지 보존 | 응답의 원본 페이지 번호로 파일 생성 | 5·9페이지를 1·2페이지로 당겨 저장하지 않음. 요소 순서와 공백 결합 방식·Markdown 내용 보존 |
| 결과 보호 | 기존 출력 경로 거부, 임시 결과 작성 후 새 폴더로 이동 | 기존 자료를 덮어쓰거나 이전 실행의 뒤쪽 페이지와 섞지 않음. Windows의 같은 상위 경로에서 확정 동작 검증 |
| 오류·빈 결과 | 오류는 종료 코드 2, 전체 빈 결과는 저장하지 않음 | API 오류가 ‘0개 저장 성공’으로 끝나던 동작 제거 |
| 검토 상태 | 누락 가능 페이지·빈 일부 페이지·미확인 총수·이미지 참조·PDF 경고 기록 | 결과가 저장되어도 검토가 필요하면 종료 코드 1, 자동 점검 항목이 없으면 0 |
| 키 조회 | 환경 변수 우선, 필요하면 명시적 `--env-file` | `.env`를 import 시 자동 탐색하거나 프로세스 환경에 키를 다시 쓰지 않음. 기존 `.env` 사용자는 파일을 명시 |

요청과 응답 해석의 기준으로 PyPI의 `langchain-upstage 0.7.7`, `langchain-core 1.2.21` 배포 소스를 확인했다. `aload()`는 Python 실행기에서 동기 로더를 실행하는 경로이며, Upstage 서버의 별도 비동기 작업 API를 사용하는 것이 아니다. 단일 PDF 입력은 `lazy_load()`에서 페이지별 요청, 비PDF는 전체 요청이었음을 확인했다.

관련 공식 문서: [Upstage Document Parse](https://console.upstage.ai/api/parse/document-parsing), [지원 형식과 요청 한도](https://console.upstage.ai/docs/models/document-parse), [HTTPX timeout](https://www.python-httpx.org/advanced/timeouts/). 현재 동기 API의 파일 한도는 요청당 100MB, 비PDF 문서 페이지 한도는 100쪽으로 다룬다. PDF는 각 요청 파일의 크기를 검사한다.

## 결과·보존 계약

- 입력을 한 번 읽은 스냅샷과 SHA-256을 사용한다. 그 뒤 입력 경로의 내용이 바뀌어도 전송 데이터와 manifest 식별 정보가 어긋나지 않는다.
- `parsing_page_N.md`의 N은 원본 페이지 번호다. `manifest.json`에 원본 이름·크기·해시, 결과 해시, 요청 옵션, 반환 모델, 전체/저장 페이지 수, 페이지별 요소 수·좌표, 검토 항목과 패키지 버전을 남긴다. API 키와 전체 로컬 경로는 넣지 않는다.
- PDF는 원본의 총 페이지 수를 알고 있다. 다른 형식은 API `usage.pages`가 있으면 이를 쓰고, 없으면 총 페이지 수를 미확인으로 둔다. 내용이 없는 페이지를 빈 페이지와 추출 실패 중 어느 하나로 단정하지 않는다.
- 빈 PDF 페이지가 섞여 있으면 뒤쪽 원본 번호를 유지하고 검토 항목을 남긴다. 전체 결과가 비었거나 공백뿐이면 오류다. 일부 페이지의 API 요청이 실패하면 앞쪽 결과도 완료 폴더로 저장하지 않는다.
- 이미지 실물 추출은 이번 범위에 포함하지 않았다. 일반 Markdown·HTML 참조를 점검하며 로컬 이미지는 미해결, 원격 주소는 미확인으로 기록한다. 원격 주소를 방문하거나 임의 경로의 파일을 복사하지 않는다. 복잡한 Markdown 문법 전체를 해석하는 렌더러는 아니다.
- 원격 오류 본문·요청 비밀값을 출력하지 않는다. PDF 라이브러리 경고는 처리 구간에서 건수만 수집하고 원래 로깅 설정을 복원한다. 문서 내용은 사용자가 지정한 결과 파일에만 기록한다.
- 기존 `target_doc.hwpx`와 `parsing_result/`의 Markdown 84개는 그대로 보존했다. 새 이미지 참조 검사에서도 기존 결과의 미해결 로컬 참조 14개를 확인했다. 기존 결과를 이번 API 실행 결과로 제시하거나 수정하지 않았다.
- 완료된 세 폴더와 위 자료를 합한 **144개 파일**의 작업 전후 해시가 동일했다. 완료된 세 폴더의 테스트는 재실행하지 않았다.
- 대체 구현 검증 후 `parsing.py`를 삭제했다. `config.py`는 실행 시 설정을 읽도록 개편했다. 호환용 실행 파일은 남기지 않았다.
- `requirements.txt`를 UTF-8로 정리하고 직접 의존성을 HTTPX·pypdf·python-dotenv로 축소했다. LangChain/OpenAI 경유 의존성은 사용하지 않는다. `.gitignore`에는 새 `outputs/`와 Python 캐시만 추가했다.
- 사용자 승인에 따라 폴더명을 `document_parser`로 변경했다. 변경 직후 대상 폴더 97개 파일과 기존 세 폴더의 전체 파일 해시가 변경 전과 같음을 확인했다. 이후 이 검증 기록과 루트 인계 문서의 현재 경로·상태만 갱신했다. 커밋·푸시는 하지 않았다.

## 실제 검증 결과

2026-11-17 Windows, Python 3.13.2의 전용 임시 환경에서 실행했다.

- 환경: `%TEMP%\etc-document-parsing-runtime\Scripts\python.exe`
- 직접 의존성: HTTPX 0.28.1, pypdf 6.9.2, python-dotenv 1.2.2.
- 구현 완료 시 실행: **39개 통과**, 건너뜀 없음. 기록 시간 8.949초.
- 이름 변경 후 `document_parser`에서 최종 재실행: **39개 통과**, 건너뜀 없음. 기록 시간 9.445초. 실제 API 호출 없이 같은 모의 HTTP 검증을 수행했다.
- `uv pip check`: 설치된 9개 패키지의 호환성 확인.
- Python 구문 검사·함수 문서 문자열 확인, `git diff --check` 통과.

| 범위 | 결과 |
| --- | --- |
| 요청·응답 18개 | 가상 HWPX 전체 전송, 실제 생성한 가상 PDF의 한 페이지씩 분할, 여섯 요청 필드와 인증 헤더, 원본 페이지 오프셋, 좌표·내용 보존 |

검증 전 파일 쓰기와 네트워크 경로를 확인했다. 모든 검증 입력은 가상 바이트나 pypdf로 생성한 빈 PDF이며, 저장은 `TemporaryDirectory`에 격리했다. HTTPX `MockTransport`로 응답을 제공하고 실제 HTTP 전송 경로를 실패하도록 막았다. CLI 시험의 새 프로세스에서는 실제 `UPSTAGE_API_KEY`를 제거하고 시험용 값만 사용했다. 기존 HWPX 원문은 API로 보내지 않았다.

위 결과는 로컬 처리·요청 계약·가상 응답 검증이다. 실제 Upstage API 성공이나 OCR 품질을 재현한 결과가 아니다.

재실행은 대상 폴더에서 한다.

```powershell
$runtimePython = Join-Path $env:TEMP 'etc-document-parsing-runtime\Scripts\python.exe'
& $runtimePython -B -m unittest discover -s tests
```

## 미검증 범위

- 실제 API 인증·과금·응답 품질·서비스 부하·모델별 동작.
- 기존 HWPX 원본과 Markdown 84개의 원문 대비 정확도·완전성.
- 실제 HWP/HWPX·Office·이미지 문서의 OCR·표·읽기 순서 품질. 가상 HWPX 바이트는 클라이언트 전송 시험 자료이며 유효 문서 변환 시험 자료가 아니다.
- 이미지 파일 추출·다운로드, 복잡한 Markdown 전체 문법, 서버 비동기 작업 API, 대용량 장시간 실행.
- 다른 운영체제의 폴더 확정 동작, 네트워크 드라이브, 강제 프로세스 종료·전원 차단 시 임시 폴더 정리. 일반 예외와 정상 취소에 대한 파일 보존 검증과 구분한다.
- 실제 개방 완료·평가 인정·개인 또는 기관 성과.
